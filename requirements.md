| SR-01 | **MFA (TOTP) for all AEC staff and delegate accounts.** As an AEC staff member or state Commissioner's delegate, I must enter a time-based one-time password (TOTP, RFC 6238) in addition to my password before a session is issued, so that a phished or stolen password alone cannot give an attacker access to enrolment, candidate or result functions. | High | Medium | Toukir |
| SR-02 | **Role-based access control with least privilege, enforced server side.** As the platform owner, I need every request authorised on the server against the caller's role, with deny by default, so that a user can perform only the actions their role requires and hiding buttons in the UI or altering client requests cannot bypass permissions. | High | Medium | Toukir |
| SR-03 | **Login protection: Argon2id hashing, lockout and rate limiting, all attempts logged.** As the platform owner, I need passwords stored only as salted Argon2id hashes, accounts temporarily locked after repeated failed logins, login requests rate limited per account and per IP, and every login attempt logged, so that brute-force and credential-stuffing attacks are slowed, and a database leak does not expose usable passwords. | High | Medium | Toukir |
| SR-04 | **Tamper-evident, hash-chained audit log for all admin and roll changes.** As an auditor, I need every administrative action and electoral-roll change recorded in an append-only log in which each entry includes a hash of the previous entry, so that any edit, deletion or reordering of past entries is detectable by a verification routine and each change can be traced to a user, time and before/after value. | High | High | Toukir |
| SR-05 | **Encryption of elector personal data at rest.** As an elector, I want my name, date of birth and address unreadable to anyone who obtains the database or a backup, so that a data leak or insider copy does not expose my identity details. **Requirement:** The system shall encrypt each of these fields separately with AES-256-GCM, using a fresh random nonce per value and the table and column name as associated data, so a value moved into another column fails to decrypt. The key shall be separate from the database and from every other key. Audit entries shall never contain the personal values. Email and electoral division are intentionally left unencrypted, because email is needed to log in and division is needed to count votes. **Threat:** Information disclosure of the electoral roll through database access, backups or insider copying.| High | Medium | Kaushik |
| SR-06 | **Server-side session management with timeouts and re-authentication.** As the platform owner, I need every login session to be revocable and time-limited on the server, so that a stolen or copied cookie cannot be used after logout or inactivity.**Requirement:** The cookie shall carry only a random session ID, and only its SHA-256 hash shall be stored. Sessions shall expire after 15 minutes idle or 8 hours total. Logout and "sign out everywhere" shall revoke sessions immediately. Staff accounts shall have one active session. Sensitive changes shall need the password re-entered within the last 5 minutes. **Threat:** Session hijacking and reuse of stolen cookies. | High | Medium | Kaushik |
| SR-07 | **Two-person approval for bulk export of elector records.** As the platform owner, I need large exports of the roll to be approved by a second officer, so that one insider cannot copy the roll alone. **Requirement:** Exports of up to 500 records may be approved by the requester. Exports above 500 records shall need approval from a second enrolment officer, never the requester. A written reason shall be required. A request shall expire after 24 hours. An approved export shall be downloadable once, by the requester only, and shall be refused if the roll has grown beyond the approved record count or beyond 500 records, whichever is larger. Spreadsheet formula characters shall be escaped. Audit entries shall record counts, never personal data. **Threat:** Bulk data theft by a malicious insider. | High | High | Kaushik |
| SR-08 | **Secure build pipeline and supply-chain checks.** As the platform owner, I need every code change automatically tested and scanned, so that vulnerable dependencies or insecure code do not reach a release unnoticed. **Requirement:** Every push and pull request shall run the unit tests, static analysis, dependency vulnerability scanning and linting, and shall produce a software bill of materials. Third-party pipeline actions shall be pinned to a full commit hash. Pipeline permissions shall be read-only by default. Releases shall have checksums and signed build provenance. **Threat:** Compromised or vulnerable third-party components and tampered builds. | Medium | Medium | Kaushik |
| SR-09 | **One vote per voter.** As an electoral commissioner, I want each registered elector to be able to cast at most one ballot, so that duplicate voting is prevented and election integrity is maintained. **Requirement:** The system shall enforce atomic one-vote restriction using a single conditional database update (`UPDATE voters SET ballot_issued = TRUE WHERE id = :id AND enrolled = TRUE AND ballot_issued = FALSE`). The database shall reject any attempt by an ineligible elector or an elector who has already been issued a ballot, with zero possibility of race conditions under high concurrency. **Threat:** Double voting, electoral fraud, race-condition exploitation during concurrent ballot submission. | High | Medium | Sehara |
| SR-10 | **Signed voter receipt with tracking code.** As a voter, I want a verifiable cryptographic receipt with a unique tracking code after voting that proves my vote was recorded, without revealing which candidates I voted for. **Requirement:** The system shall generate a unique tracking code and compute an HMAC-SHA256 digital signature over the tracking code using the server receipt secret key. The receipt must reveal NO voting choices or ballot preferences. The receipt record must be returned upon successful atomic ballot commit. **Threat:** Receipt forgery, repudiation of recorded votes, violation of ballot secrecy through choice leakage. | High | Medium | Sehara |
| SR-11 | **Server-side ballot and input validation.** As the platform owner, I need candidate preferences validated strictly on the server side prior to processing, so that malformed or malicious ballots are rejected before database modification. **Requirement:** The server shall validate ballot structure and preferential ranking rules prior to any database operation: candidate IDs must be unique, ranks must start at 1, rankings must be contiguous (1..N) without gaps or duplicates, and all SQL queries must be strictly parameterized. **Threat:** SQL injection, invalid ballot injection, preferential voting ranking corruption. | High | Medium | Sehara |
| SR-12 | **Diplomatic mission IP restriction for overseas access.** As the platform owner, I need overseas voting submissions restricted exclusively to verified diplomatic mission networks, so that unauthorized external access is blocked. **Requirement:** The system shall validate client IP addresses against configured CIDR ranges (`DIPLOMATIC_MISSION_IP_RANGES`). The server must use the authoritative, server-observed `remote_addr` and reject spoofed headers (`X-Forwarded-For`, `X-Real-IP`). Missing or empty configuration must deny access by default (HTTP 403 `IP_NOT_ALLOWED`) with zero database side-effects. **Threat:** IP spoofing, unauthorized voting from non-diplomatic foreign networks, parameter tampering. | High | Medium | Sehara |
| SR-13 | **13 Ballot encryption: These protect the ballot itself from the moment it leaves the voter's browser until it is counted: secret, unlinkable, unaltered, and sent over a hardened connection** As a voter, I want my ballot unreadable to everyone except the official count, so that no system administrator, attacker or other subsystem can see how I voted. Requirement. At submission the system shall encrypt each ballot with a fresh AES-256-GCM key, and wrap that key with the tally's RSA-3072 OAEP public key. The voting service shall hold only the public key, so stored ballots can't be read back by it. No ballot shall ever be written to storage or logs in plaintext. Threat: Information disclosure of vote choices through database access, backups or logs. Ballot secrecy is the platform's core property in every A1.| High| High | Mykhailo |

After the eligibility check, the voter shall receive a random one-time ballot token, and only its SHA-256 hash is stored, with no voter ID. The ballot shall be cast with the token alone, without the login session. Ballots and tokens shall carry no voter ID, timestamp or IP address. Threat. Re-identification of voters by insiders correlating identity, timing and ballot records.| High | High | Mykhailo |

| SR-17 | **Dual control for candidate changes and manual exclusion:** As a candidate I need every change to the candidate list or ballot order and any exclusion during a court-ordered recount approved by two different delegates so that no single insider can alter or remove a candidate. **Requirement:** A create update or exclude request shall only take effect after a second delegate from the same state approves it. The requester may withdraw but never approve or reject their own request. Every request needs a written reason of 10 to 500 characters and expires after 24 hours. Only one request per candidate may be pending two candidates may not share a ballot position in a division and new candidates may only be placed in an existing division. Candidate details freeze once voting starts exclusions stay allowed for recounts and the tally then counts each affected ballot for the voter's next preference. Approval is atomic and every request approval rejection withdrawal and self-approval attempt is audited with before and after values. **Threat:** A single malicious or compromised delegate tampering with the ballot. | High | High | Osanda |
| SR-18 | **Signed and timestamped results package:** As a member of the public or media I need published results to carry a digital signature I can check so that I know they came from the AEC and were not altered. **Requirement:** After each tally that passes reconciliation the system shall build an aggregate-only package containing per-division totals for every candidate including those with zero votes plus excluded candidates and no ballot-level data. It shall serialise the package as canonical JSON with the election ID a sequence number and a UTC timestamp then sign it with the current Ed25519 results key from SR-20. The key ID shall be included so older packages still verify after a key rotation. If reconciliation fails no package shall be signed or published. Anyone shall be able to view download and verify the latest package including offline with the published public key. **Threat:** Tampering with or spoofing of published results and replaying an old result as the latest. | High | Medium | Osanda |
| SR-19 | **Reconciliation of voters ballot tokens and stored ballots:** As an auditor I need the number of voters issued a ballot to match the ballot tokens and the stored ballots so that stuffed deleted or forged ballots are detected even though ballots cannot be linked to voters. **Requirement:** The system shall check that tokens issued equal voters marked as issued and that ballots stored equal tokens used both in total and for every division. Unused tokens shall be reported not treated as errors. The check shall run before every tally on demand for tally officers and auditors and from a command-line job that exits with an error on mismatch so it can be scheduled daily. Each mismatch shall raise one integrity alert and an audit entry and a failed reconciliation shall block the publication of results under SR-18. **Threat:** Ballot stuffing deleted ballots and resetting a voter's voted flag. | Medium | Medium | Osanda |
| SR-20 | **Key management:** As the platform owner I need each cryptographic purpose to use its own protected key so that leaking or misusing one key does not compromise the others. **Requirement:** Ballot encryption ballot integrity audit log MFA and results signing shall each use a separate key generated outside the source tree and a test shall fail if private key material appears in the repository. Private and secret keys shall be encrypted at rest with a key derived from KEY_PASSPHRASE using scrypt and AES-256-GCM and the passphrase shall be mandatory in production with a minimum length of 16 characters. The app shall refuse to start if key files are readable by other users on Linux and macOS. Results signing keys shall be versioned and rotated only through a server-side command keeping old public keys so earlier signatures still verify and every rotation shall be audited. **Threat:** Key disclosure through a stolen disk backup or repository and reuse of one key across purposes. | High | High | Osanda |
